# M8 multi-device synchronization

## Deployment status

The application keeps working in IndexedDB without a remote connection. An opt-in M8 Vercel Preview needs a separately reviewed PostgreSQL environment. Use an isolated database and synthetic records for validation. The existing M7B runtime and production schema are outside this migration. Automatic Git deployments are disabled for the M8 branch.

1. Review and apply `server/sync-schema.sql` and `server/sync-runtime.sql` with a direct TLS-verified operator connection in the isolated environment. Give `livestock_sync_runtime` a private password and enable login under operator control. Check effective permissions, including inherited `PUBLIC` privileges. Store the pooled runtime URL privately with `sslmode=verify-full`. Keep the owner and M7B roles out of the M8 runtime.
2. Configure `SYNC_ENABLED`, `SYNC_DATABASE_URL` and `SYNC_ALLOWED_ORIGIN` for the M8 Preview branch. The exact Preview HTTPS origin is used for CSRF protection. The API also checks Vercel's Preview environment and the database username. Keep credentials in server-only environment variables. Protected Preview is appropriate while validating with test data.
3. Run `node scripts/sync-bootstrap.mjs "Farm name" <absolute-private.sync-grant>` on a trusted operator host with `SYNC_OPERATOR_DATABASE_URL` configured. Use an owner-only directory outside Git, with restrictive Windows ACLs where applicable. Transfer the one-use code privately. It expires after 15 minutes. A bootstrap invocation creates a new farm, so use it once for each intended farm.
4. In Settings, enroll the first device, review both record lists, and confirm reconciliation. For subsequent devices issue an invitation from an already authorized device. Enrollment issues a server-created device identity and an opaque 90-day cookie. Revoked cookies cannot read or write server data. Revocation does not erase data already cached on that device. Use the owner's existing authorized device or operator-managed recovery when a session expires. Retry receipts are owner scoped so re-enrolling the same owner can recover a pending operation whose response was lost.
5. Verify on authorized desktop, iPhone, and Android installations. Create a record offline, reopen and reconnect, then open or manually sync another device. Try two edits from the same revision and inspect both versions before choosing. Keep an independent v1 backup. Disable the Preview opt-in to stop existing remote access without removing local records.

## Data and conflicts

Stock PostgreSQL tables separate the farm and identity model, animals, catalogue, health events and details, receipts, and tasks. Per-table validated payloads preserve existing record shapes. Generated columns and scoped foreign keys enforce parent and clinical associations. A per-farm transaction lock serializes usage of the cursor and revision checks. Receipts, current server rows, and change-log entries commit together. A repeated UUID returns the original outcome for its owner when the operation fingerprint matches. Clinical entries and original batch receipts are append-only. A rejected amendment branch stays available locally so the owner can review the authoritative history and record a new amendment. Tasks support tombstones for unlinked tasks. Animal removal is represented by archive status. No server change is ordered by a client timestamp.

IndexedDB v5 adds the outbox, cursor binding and server revisions. The veterinary repository queues an entire batch in the same transaction as its local records. A failed request preserves the operation, and the coordinator retries with bounded backoff. Pages are applied with their cursor in an IndexedDB transaction. Conflicts hold both versions for review and suspend further sends until resolved. Constraint conflicts between different IDs may require correcting the local record before retrying. The initial merge preserves animal and clinical UUIDs, verifies record relationships, and explicitly lists any matching species identifiers that are consolidated. The API accepts at most 4,000 changes and 3 MiB per operation, and caps each remote record payload at 24,000 UTF-8 bytes. Very large initial imports need a separately planned staged import.

Backups keep format v1 and payload schema v4. Sync credentials, operational metadata and the remote history are outside the backup. Finish queued changes, switch to local mode in Settings, and restore the backup before explicitly reviewing reconciliation again. A connected restore is blocked to prevent silent bulk replacement. Local photographs, audit entries and per-device preferences remain in backups. Keep independent backups of devices with pending or unsynchronized content.

## Access and photographs

Farm membership is established by a server-issued grant tied to a stable UUID. Every sync, device and invitation action resolves the session cookie to an active server-side record. This milestone authorizes owner devices only. A future identity provider can replace operator bootstrap while preserving principal, farm and device IDs. Add server-side read-only capability checks before granting a veterinarian identity access.

Remote photos are pending a storage decision. The private storage interface checks MIME type, size and SHA-256 and can reuse a verified cached blob. Before enabling uploads, approve a private bucket or isolated private database blob store, its limits, and its retention policy. For larger installations, private S3-compatible storage can keep photo traffic separate. PostgreSQL blob storage avoids another account for a small trial, but consumes database storage and transfer. Neither is activated in this milestone.
